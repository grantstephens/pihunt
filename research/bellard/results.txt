# Update 5 (2026-10-07, same session): root-caused Update 4's gap with perf (installed partway
# through, with the user's go-ahead, specifically to stop guessing -- see README.md). numv/denv
# were spilled to the stack and reloaded every k instead of staying in YMM registers; one reload
# alone was ~25% of the hot function's own samples. Two targeted fixes tried (isolating the
# update into its own #[inline(never)] call; shrinking the per-lane batch buffers from 512 to 64
# to cut stack-frame pressure) -- neither closed the gap (the first measured slower, ~0.95-1.03s;
# the second was within noise of the original, ~0.89-0.93s, and re-profiling showed the exact
# same spill instruction, same ~28% share, unmoved). Confirmed root cause, no fix found this
# round; both experiments reverted, pi1-simd4 unchanged from Update 4's numbers above.

# Update 6 (2026-10-07, same session): static disassembly (objdump, no profiler needed) ruled out
# register scarcity directly -- only 5 of 16 YMM registers in use in frac4_avx2, both montmul4
# calls confirmed inlined (no call instruction for them). Then tried the user's suggested
# assembly route: two asm! register-pin hints (one-sided at the write end, then symmetric at
# both read and write ends) forcing numv/denv into specific unused registers at precise program
# points, without touching the real arithmetic. Both: identical spill, identical instruction,
# timing unchanged (~0.93s, if anything marginally worse from the extra asm overhead). Four
# independent targeted interventions now produce the exact same result -- strong evidence this is
# an LLVM loop/PHI-node-level storage decision, not fixable by hints at the use sites. A real fix
# would need the whole update rewritten as one opaque hand-written asm block (not attempted --
# materially larger, correctness-critical undertaking; see README.md). pi1-simd4 unchanged.

# Update 7 (2026-10-07, same session): tried a third, structurally different angle --
# vectorising flush_lane's batched-inverse extraction instead of the main loop (no loop-carried
# dependency between items once ib[i] is known, single shared modulus -- neither property the
# main loop's spill needed, so a genuinely different bet). Split the single reverse pass into
# computing+storing ib[] (unchanged, sequential) then a vectorised extraction pass over groups
# of 4 independent items via montmul4. Measured ~29% SLOWER (0.91s -> 1.15s at n=2e4), not an
# improvement. Isolated why: a scalar-but-still-two-pass version (same split, no montmul4) matched
# the original single-pass baseline exactly (~0.91s) -- the split itself is free. The entire
# regression is the vectorisation, most likely the pa[be[i]] gather (four data-dependent indices,
# not a contiguous load like the main loop's term arrays) costing more to assemble/unpack than
# the three scalar multiplies it replaces. Reverted cleanly (confirmed via git diff --stat
# matching the pre-experiment size exactly). pi1-simd4 unchanged from Update 4's numbers.
